# Shadow Coach

> Things I’ve shipped：ShadowCoach https://www.shadowcoach.cn/

ShadowCoach 是一款 AI 简历优化工具。用户上传简历并输入目标岗位 JD 后，系统会分析岗位要求与候选人经历，识别信息缺口，必要时主动追问，再生成针对岗位优化的简历。

//我通过这个项目跑通了从需求调研、产品设计、Agent 架构迭代，到登录、支付和部署的完整 Vibe Coding 流程。

---

## 1. WHY：为什么做这个项目

### 从想法拆解到需求收缩

最初，我想寻找一个可以由个人完成闭环的项目，验证“一个人 + AI”能否真正完成从需求发现、产品开发到获得商业收入的全过程。以此为目标，我认为项目选题需要满足以下条件：
 - 存在真实需求、目标用户和可验证的市场
 - 有竞品未满足的需求空间
 - 可以在线完成获客、使用和付费，不依赖线下资产、地推或专业知识库
 - 不涉及医疗、法律等高风险决策场景，降低错误结果可能带来的严重影响；
 - 实现复杂度可控，能够快速推出 MVP 并验证核心需求。
求职辅助与职业规划 Agent 基本符合这些条件。但完整的职业规划涉及大量场景，初期范围仍然过大，因此我先将需求收缩为一个更明确的任务：
> 根据目标岗位的 JD，帮助用户有针对性地优化简历。
接下来需要验证两个问题：用户是否确实存在这一需求，以及现有产品为什么还没有充分解决它。

### 需求与竞品调研
需求上，社交平台上可以看到有大量用户找业内资深人员辅助修改简历、模拟面试等求职诉求，Agent的目标应当是能够达到真实资深从业者的修改水平与信任感。其次，在求职时针对不同JD，用户常有进行针对性微调的诉求，产品能一键调整优化，省时省力。
已有的产品上，当前可以分为两类：
1. **通用AI**
	使用 ChatGPT、DeepSeek 等通用模型优化简历很方便，但实际效果并不稳定。
	- 模型容易停留在关键词匹配，没有理解岗位真正关注的能力；
	- 为了迎合 JD，可能添加用户没有提供的经历或成果，难以建立信任；
	- 多轮修改时，局部要求可能导致整份简历发生变化，部分产品无法直接输出文档结果。
2. **简历修改的垂类产品**
	主要集中在简历模板、ATS 评分、JD 匹配和一键改写。
	- 优化结果偏重关键词和格式，缺少对经历结构与叙事逻辑的改善；
	- 修改过程缺少原因说明，用户难以判断内容是否可信；
	- 对局部修改和多轮持续优化的支持有限。

### ShadowCoach 的切入点
基于这些观察，我为 ShadowCoach 确定了三个核心方向：
1. **让简历表达更清晰、更契合、更可信**
   优化经历的结构和叙事逻辑，避免流水账式描述，并说明关键修改的原因。生成前抽取简历事实，生成后检查新增内容和修改范围，避免编造经历。
2. **在证据不足时主动追问**
   识别简历与 JD 之间的证据缺口。当关键信息不足时，先向用户提问，再使用用户确认过的事实进行优化。
3. **支持可控的持续修改**
   用户可以通过多轮对话继续调整简历，也可以只修改指定部分，避免一个局部要求影响全文。最终结果可以直接导出使用。

## 2. HOW：产品方案与架构演进

### 产品功能：从一次生成到持续优化

ShadowCoach 的第一版只完成了一件事：用户上传简历和目标岗位 JD，系统生成一份优化稿。这个流程适合快速验证需求，但一次生成很难直接得到可以投递的最终版本。

用户通常还会继续提出更具体的要求，例如强化某段经历、调整表达语气、压缩内容，或者只修改其中一个模块。因此，第一个重要改动是加入**多轮对话持续调优**：系统保留当前版本和对话上下文，用户可以围绕已有结果继续修改，而不必每次重新生成整份简历。

第二个改动来自另一个更关键的问题：当 JD 需要某项能力，而用户简历中没有相关信息时，系统不应该直接猜测或跳过。为此，我加入了**证据不足时主动追问**的能力。系统先识别岗位要求与现有经历之间的信息缺口，再决定直接生成，还是先请用户补充事实。

产品流程因此从一次改写，逐步演进为：

```text
上传简历与 JD
→ 分析岗位和候选人经历
→ 判断证据是否充分
→ 主动追问或生成优化稿
→ 查看修改原因
→ 通过多轮对话继续局部优化
→ 导出简历
```

这两个功能改动也推动了底层架构的持续调整。

### 第一阶段：单 Prompt + Dify

第一版采用单 Prompt：模型在一次调用中完成 JD 理解、简历分析和内容改写。工作流最初通过 Dify 实现，优点是搭建速度快，适合验证最基本的产品链路。

但在持续测试中，单 Prompt 的问题反复出现：

- 同一份输入多次生成，优化结果差异较大；
- 多轮对话缺少稳定记忆，前后内容和格式容易跳变；
- 用户只要求修改局部内容时，模型可能改动整份简历；
- 对经历的结构化和表达逻辑优化不足；
- 某些情况下输出与原文几乎没有区别，没有产生实际优化。

与此同时，Dify 在较长任务中频繁出现超时。它适合快速搭建原型，但无法满足生产环境对稳定性、超时控制和问题排查的要求。

这些现象说明，继续在一个 Prompt 中增加规则并不能解决根本问题。岗位分析、事实理解、结构规划和文字改写需要被拆开处理，多轮状态也需要由系统显式管理。

### 第二阶段：多阶段固定 Workflow

第二版将一次大模型调用拆分为多个固定节点：

```text
解析简历与 JD
→ 分析岗位要求
→ 抽取候选人经历
→ 规划优化方向
→ 生成简历
→ 检查结果
```

每个节点只负责一类任务，使输出比单 Prompt 更稳定，也更容易定位问题。多轮修改时，系统可以保留当前简历版本，并将修改范围传递给对应节点，从而减少无关内容和格式发生变化。

这一阶段也将模型调用从 Dify 迁移到 Node.js 后端直连。系统可以自行管理调用超时、失败重试、阶段日志和模型参数，更适合继续开发和线上运行。

固定 Workflow 改善了稳定性，但仍然存在两个明显限制。

第一，不同岗位关注的核心能力并不相同。固定节点可以完成通用分析，却很难根据具体 JD 动态决定应该重点判断哪些能力，以及是否需要调整简历结构。

第二，当简历缺少岗位需要的相关经历时，固定流程仍然会继续执行，不会主动暂停并要求用户补充信息。

这两个问题都需要系统根据当前上下文动态决定下一步，而不是始终执行相同的节点顺序。

### 第三阶段：在固定流程中引入 Agentic Workflow

第三版没有推翻原有 Workflow，而是在关键判断环节引入 Agentic Workflow。

Agent 先结合 JD 和候选人经历判断当前岗位最需要关注的能力，再决定后续应该使用哪些分析与改写步骤。如果关键能力缺少事实支持，Agent 可以暂停生成并发起追问；用户补充信息后，再回到后续优化流程。

它主要解决了两个问题：

1. 针对不同岗位识别不同的分析重点，并据此调整简历的内容重点和结构；
2. 在证据不足时主动追问，而不是继续生成或编造内容。

固定 Workflow 继续负责简历解析、事实抽取、内容生成和结果检查等相对确定的任务；Agent 只负责那些需要根据上下文动态判断的环节。最终形成的是固定流程与 Agent 决策结合的混合架构。

### 为什么没有直接改成纯 Agent 架构

引入 Agentic Workflow 后，一个自然的问题是：为什么不让 Agent 接管整个流程？

首先，现有固定 Workflow 已经跑通，通用场景下的效果也基本可用。完全重构为纯 Agent，意味着重新设计工具、状态、上下文和执行边界，改动成本较高，也会增加新的不确定性。

其次，完整流程的调用时间已经较长。如果每一步都由 Agent 动态规划和调用，整体延迟与模型成本还会继续上升，而用户未必能够感知到对应的价值提升。

因此，我选择先保留已经有效的固定流程，只在它无法解决的动态判断环节引入 Agent。先跑通完整产品闭环，再根据真实使用中的问题继续迭代，而不是为了架构形式提前完成一次大规模重构。

### 模型选择：中文能力接近时优先考虑成本

在模型选择上，我主要比较了 DeepSeek、Kimi 和 GPT 的中文简历改写表现，包括语言自然度、结构调整和对修改要求的理解。

从现阶段的主观测试体感来看，三者在这个任务上的差距并不明显，还不足以抵消调用成本上的差异。因此，实验阶段优先使用 DeepSeek Pro，同时保留模型切换能力，便于后续根据质量、速度和成本继续比较。

### 从原型补齐为可使用的产品

AI 工作流跑通后，项目仍然只是一个功能原型。为了完成从使用到交易的闭环，我继续补齐了文件解析、登录、额度、支付、版本管理、导出和服务器部署等能力。

目前 ShadowCoach 已实现：

- Word、PDF 和文本简历输入；
- JD 匹配与能力诊断；
- 证据缺口识别与主动追问；
- 简历生成和局部多轮优化；
- 修改高亮、原因说明与版本管理；
- TXT、Word 和 PDF 导出；
- 登录、额度和支付宝支付；
- 多模型适配、超时重试与服务器部署。

## 3. Thoughts & Experiences：复盘体会

### 复杂任务中，Prompt 不能替代架构

Prompt 适合约束单次任务，但当任务同时涉及理解、判断、状态变化和结果验证时，继续增加规则只会把复杂度藏在一段文本里。

更有效的方式是拆分职责：让每个阶段只处理一类问题，并通过明确的输入、输出和校验条件连接起来。架构并不能保证模型永远正确，但可以让错误更容易发现、定位和修复。

### Agent 的价值不是“自主”，而是处理不确定性

这个项目最初并不需要 Agent。固定 Pipeline 已经能够完成大部分简历改写任务。只有当系统需要根据证据是否充分，动态决定继续生成还是向用户追问时，Agent 才开始产生实际价值。

因此，是否使用 Agent 不应该取决于技术是否流行，而应该取决于流程中是否存在无法提前写死的判断。

与此同时，Agent 的自主性需要边界。事实来源、合法动作、状态变化和停止条件仍然由代码控制。在简历这种强调真实性的场景中，可控性比自由度更重要。

### 追问不是生成失败，而是产品能力

很多 AI 产品默认用户提交信息后就应该立即给出答案。但信息不足时，立即生成往往意味着猜测。

与其输出一份流畅但失真的简历，不如先提出一个准确的问题。一次好的追问可以补充事实、校正理解，也能让用户知道系统为什么无法直接下结论。

从这个角度看，追问不是模型能力不足的补救措施，而是人机协作流程的一部分。

### 生成与验证应该是同一个闭环

模型输出足够流畅时，人很容易忽略其中的事实错误。仅依赖用户阅读检查，会把产品本应承担的风险转移给用户。

因此，Verifier 不只是一个技术模块，也代表一种产品判断：系统不仅要生成结果，还应该尽可能检查结果是否遵守事实边界和用户指令。

### Vibe Coding 改变了瓶颈，但没有替代产品判断

AI 显著提高了页面开发、代码修改和问题排查的效率，让一个人完成前后端、模型接入、支付和部署成为可能。但实现成本下降之后，真正的瓶颈转移到了需求选择、质量标准和架构取舍。

AI 可以快速生成一个可运行的版本，却不会自动判断这个功能是否值得做、结果是否足够可信，以及什么时候应该停止增加功能。因此，Vibe Coding 降低了“做出来”的门槛，也让“为什么做”和“做到什么程度”变得更加重要。

### 从 Demo 到产品，主要工作发生在主流程之外

“输入简历和 JD，输出优化稿”很快就能做出演示，但一个真实可用的产品还需要处理文件格式、登录状态、额度、支付、失败重试、版本恢复、结果导出和线上部署。

这些工作不一定展示模型能力，却直接决定用户能否顺利完成一次完整任务。对个人开发者而言，跑通主流程只是开始，补齐异常与交易闭环才是从 Demo 走向产品的关键一步。

## 总结

ShadowCoach 从一个单 Prompt 的简历优化页面，逐步演进为一套能够分析、追问、改写和校验的受控 Agent Loop，也让我完整经历了一次从需求判断到产品上线的 Vibe Coding 实践。

这个过程中，我逐渐形成了一个更明确的分工原则：

> 让模型负责理解与生成，让 Harness 负责上下文、状态、事实与执行边界。
